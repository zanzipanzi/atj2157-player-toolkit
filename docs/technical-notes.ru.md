# Технические заметки: плееры-«клоны iPod nano» на Actions ATJ2157

Всё здесь измерено на **одном** экземпляре (обычный MP3/MP4-плеер на чипе Actions **ATJ2157**, ARM Cortex-M4F, прошивка
на SPI-флешке **GD25Q32** на 4 МиБ, медиа на microSD, строка версии прошивки `1.101.56`). У других плееров с тем же чипом,
вероятно, похоже, но гарантий нет. Пометка **(unverified)** означает, что вывод сделан по чтению кода или документации и
на железе не подтверждён.

Другие языки: [English](technical-notes.md), [Українська](technical-notes.uk.md). На графиках только числа и адреса, пояснения к ним даны текстом под каждой картинкой. Где взять нужные инструменты и файлы: [where-to-get.ru.md](where-to-get.ru.md).

## 1. Как опознать устройство

| Режим | USB id | Что видно |
|---|---|---|
| обычный | `10d6:1101` | флешка, `ACTIONS USB DISK FOB 2.0`; `lsusb` может назвать её «D-Wave 2GB MP4 Player / AK1025» (старая запись в базе с тем же id, это **не** определение чипа) |
| сервисный режим ADFU | `10d6:10d6` | протокол обновления прошивки Actions, файловой системы нет |

Надёжно опознать чип можно только по ответу `adfu_info` в режиме ADFU: байты `00 'CADFUD' 30 51`, где `0x3051` означает
ATJ2157 (похожий ATJ2127 отвечает иначе). Поиск по наклейке предсказал для этого плеера не тот чип, поэтому проверяйте до
загрузки любого кода.

**Вход в ADFU.** На проверенном экземпляре: выключатель в положении OFF, зажать **центральную кнопку**, подключить USB.
Программная команда `adfu_reboot` (служебные CDB `0xCC`, затем `0xCB 0x21`) работает и из обычного режима. Выход из ADFU:
отключить кабель, выключатель OFF и снова ON, при необходимости зажать центр и MENU; программный `reset` из ADFU возвращал в
ADFU. Программа, зависшая в сервисном режиме, может оставить плеер «мёртвым» до разрядки батареи, поэтому найдите
аппаратную кнопку входа **до** того, как запустите что-то пишущее.

## 2. Протокол ADFU и карта памяти

USB Mass Storage (bulk-only) со служебными командами. CDB `0xCD` несёт подкоманду:

| Подкоманда | Смысл |
|---|---|
| `0x13` WRITERAM | записать байты в ОЗУ чипа |
| `0x93` READRAM | прочитать ОЗУ |
| `0x20` SWITCH | запустить загруженную программу-сервер (`adfus`) по адресу |
| `0x21` EXEC | выполнить код по адресу (точка входа вызывается как Thumb: адрес с установленным младшим битом) |
| `0x22` RETSIZE / `0x23` READRET | размер / байты блока результата, который вернула программа |
| `0x10`, `0x60` | доступ к флешке через штатный драйвер |

Хост-утилита - `actions_dump` из проекта [actions_flash](https://github.com/ilyakurdyukov/actions_flash); в этом
репозитории лежит только код, который выполняется внутри чипа.

Адреса, которые используют программы из [`payload/`](../payload):

| Область | Адрес | Назначение |
|---|---|---|
| adfus (программа-сервер) | `0x118000` | загружается командой SWITCH; **не** делайте SWITCH повторно для уже работающей |
| код payload | `0x11E000` | точка входа возвращает указатель на `{адрес, размер}` результата |
| ARGS | `0x120000` | входные слова для payload |
| RESULT | `0x120010` | `{указатель, размер}` |
| DATA | `0x120100` .. `0x124100` | выходной буфер (16 КиБ) |
| SRC | `0x121000` | данные для записи (пересекается с DATA; программа записи использует из DATA только первые 56 байт) |

`read_mem2` копирует через вспомогательную программу, которая ложится на `0x11E000`, поэтому payload нужно **загружать заново

Payload собирается `arm-none-eabi-gcc -march=armv7-m -mthumb` (без флагов ассемблер ругается `invalid constant ... after
fixup`: по умолчанию цель ARM, а не Thumb-2).

## 3. Загрузочное ПЗУ

64 КиБ масочного ПЗУ лежат с адреса 0 и **не** читаются обычным `read_mem`; `read_mem2` через adfus его читает. ОЗУ -
`0x100000`..`0x137FFF` (224 КиБ). Таблица векторов начинается со SP `0x00101B18` и reset `0x189`. Что показывает
дизассемблер (адреса функций - адреса в ПЗУ):

- `0x2488` main; `0x1B14` загрузка с SPI NOR; `0x1AB4` инициализация SPI; `0x383C` мультиплексор выводов; `0x31AC` чтение
  JEDEC id; `0x2224` чтение одного сектора в 512 байт (команда `0x0B` + DMA); `0x28D8` кормление сторожевого таймера.
- Кандидаты загрузки: смещения SPI `0, 0x1000, 0x10000` (таблица по адресу `0x5364`), смещения для карты `0, 0x80, 0x100, 0x200`
  (таблица по адресу `0x5370`).
- Загрузчик читает по 1024 байта с каждого смещения: сначала с **включённой** расшифровкой (`ROM_CFG+0x68 = 1`), потом с
  выключенной, и принимает блок, у которого байт 2 равен `0xA5` (или `0x5A`) и сошлась контрольная сумма (MBREC). Живой
  образ в ОЗУ по адресу `0x101000` побайтно совпал с расшифрованным сектором 0 флешки.
- **(unverified)** Слово по адресу `0xC0020000` выбирает ветку NAND, SPI или карта; ветку NAND разобрали лишь поверхностно
  (идентификатор NAND читался нулями, поэтому мы решили, что NAND нет).

## 4. SPI-флешка и шифрование

Контроллер SPI по адресу `0xC00A0000`: CTL `+0x00`, STAT `+0x04`, TXD `+0x08`, RXD `+0x0C`, LEN `+0x10`. Работают обычные
команды семейства GD25: `0x9F` JEDEC id (`C8 40 16`), `0xAB` пробуждение, `0x0B` быстрое чтение, `0x05/0x35/0x15` регистры
состояния 1-3, `0x06` разрешение записи, `0x20` стирание 4 КиБ, `0x02` запись страницы (оборачивается на 256 байтах), `0x50`
временное разрешение записи регистров, `0x01` запись регистров состояния.

**Содержимое флешки шифруется контроллером.** Сырой дамп имеет энтропию ~7,91 бита на байт и ни одной читаемой строки.
Что известно о шифраторе:

- 1492 сектора, у которых открытый текст - сплошные нули, превращаются в **один и тот же** сырой сектор: преобразование
  детерминированное и от адреса не зависит.
- Первое слово ключа блока принимает по всему дампу только 8 значений, но одна XOR-гамма образ не расшифровывает: ключ
  зависит от данных. Линейная (аффинная над GF(2)) подгонка открытого слова по текущему и предыдущим 8 или 16 словам
  шифртекста оказалась несовместной для всех 32 бит. Более сложные модели мы **не** перебирали и алгоритм офлайн не
  воспроизвели.
- Поэтому всегда работайте через аппаратуру:
  - **Чтение:** включить бит расшифровки `0x1000` в CTL (ПЗУ делает это по слову `ROM_CFG+0x68`, маска `CTL` `0xF000`).
  - **Запись:** включить бит шифрования `0x2000` только на время байтов данных команды записи. Шифратор начинает заново
    на каждой команде и считает **блок в 512 байт одним потоком**, а команда записи принимает не больше 256 байт. Рабочий приём:
    страницу A (первые 256 байт) отправить как обычно, а страницу B отправить **как передачу в 512 байт по адресу страницы B**
    (байты A, потом байты B). Буфер страницы на 256 байт в микросхеме оборачивается и оставляет последние 256 байт, а состояние
    шифратора в этот момент - правильное продолжение потока.
  - Сначала проверьте на свободном секторе: запись известного открытого текста и чтение с расшифровкой дали 0 расхождений,
    а сырые байты совпали с заводскими. Один бит `0x1000` при записи ничего полезного не делает (это бит чтения).

## 5. Защита от записи

На проверенном экземпляре `SR1 = 0x08` (BP1) и `SR2 = 0x40` (CMP): от записи защищено **всё, кроме верхних 128 КиБ**
(`0x3E0000`..`0x3FFFFF`). В верхней области лежат настройки, которые прошивка пишет сама. Запись в защищённый сектор чип
молча игнорирует: наш первый тест «прошёл» на секторе `0x3DD000`, потому что сектор был пуст и ничего не записалось, а
единственным признаком был счётчик ожидания стирания, равный 0. Всегда используйте **независимый** признак успеха
(чтение назад, счётчики опроса).

Снимайте защиту **временно**: `0x50` (временное разрешение записи регистров), затем `0x01 <SR1> <SR2>` **без** `0x06`, так
что энергонезависимые биты не меняются, а после выключения питания защита возвращается. Проверьте регистры после снятия и
верните их после записи (payload делает и то и другое и возвращает коды ошибок, см. `payload/spiwrite.c`). После входа в
ADFU `SR1` может читаться как `0x0A` вместо `0x08`: ПЗУ оставляет установленным бит WEL.

## 7. Файл шрифта NEW_M.FNT

В `NEW_M.FNT` (267 776 байт): заголовок 16 байт (`FNT`, версия 5, ячейка 14x16, размер записи 33, смещение данных `0x2810`,
1024 записи индекса); индекс из 1024 записей по 10 байт (по одной на 64 кода: `u16` число глифов до блока, `u64` карта
присутствия); 7791 запись глифа по 33 байта, отсортированные по коду; хвост 417 байт. Номер глифа = `base` + число единиц в
карте ниже бита кода. Запись - 32 байта картинки (16 строк по `ceil(ширина/8)` байт, старший бит слева) плюс байт ширины, который
означает **шаг курсора**, а не ширину картинки.

На проверенном экземпляре у всех русских глифов стояла ширина 14 (ширина иероглифа), поэтому текст шёл «вразрядку».
Исправление заменяет 66 записей (U+0401, U+0410..U+044F, U+0451) на месте узкими глифами из шрифта другого плеера Actions
(ширина 5-12, среднее 14,00 -> 7,92) и обрезает четыре глифа кавычек. Украинских букв (`Є І Ї Ґ є і ї ґ`) не было вовсе: их
добавляют, удаляя восемь римских цифр `U+2172..U+2179` и пересобирая отсортированный массив и индекс, так что размер файла
не меняется и LFI не сдвигается. Инструменты: [`tools/fnt_patch.py`](../tools/fnt_patch.py),
[`tools/fnt_add_ukr.py`](../tools/fnt_add_ukr.py). Донорский шрифт в репозиторий **не** входит (авторские права): где его взять или как собрать свободный, см. [where-to-get.ru.md](where-to-get.ru.md).

## 8. Безопасная процедура записи (то, что делает `payload/host/apply_font_fix.sh`)

1. Прочитать целевые сектора в обоих режимах и потребовать, чтобы они равнялись вашим эталонным дампам, иначе остановиться.
2. Сухой прогон: payload выполняет все проверки, но **не** посылает команд записи (возвращает код `0x10`).
3. Запросить введённое подтверждение на каждый сектор; сначала писать сектора данных, а сектор с головой LFI `0x11000` -
   **последним**.
4. Прочитать назад с расшифровкой и сравнить с целью; при любом расхождении остановиться и напечатать команду отката.
5. Откат записывает **исходные сырые байты** с выключенным шифратором (`ROLLBACK=1`). Путь сырой записи проверен на свободном
   секторе, но откат **ни разу не запускался на настоящих секторах**.

Payload отказывается писать по любому адресу вне белого списка (в нашей сборке `0x11000`, `0xE9000`, `0xEA000`, `0xEE000`),
если не передан специальный магический аргумент, требует выравнивания и длины 4 КиБ, ограничивает все циклы ожидания и
кормит сторожевой таймер. Сектор 0 (загрузочная запись) не пишется никогда.

## 9. Видео

Видеомодуль - `MMM_VP.AL` внутри LFI (адрес загрузки `0x120000`, код со смещения файла `0x1000`). По дизассемблеру и по запуску
его собственного разбора заголовка в эмуляторе ([`tools/mmm_vp_walker_emu.py`](../tools/mmm_vp_walker_emu.py)):

- Принимаются только две формы RIFF: `AVI ` и `AMV `. Остальное пишет в журнал `video format invalid!`.
- Зарегистрированы ровно один видеодекодер (`mjpeg`), один разборщик контейнера (`avi`, он же читает AMV) и один звуковой
  плагин (`wave`). H.264, XviD, DivX и MPEG-4 нет, поэтому смена кодека внутри AVI помочь не может.
- Для AVI есть жёсткая проверка раскладки: после чтения первых 512 байт байты **342..345 должны быть `AVI1`**, иначе плеер
  **молча** отказывается. Это идентификатор APP0 первого JPEG-кадра, то есть кадр должен начинаться с байта **336** с меткой
  `AVI1`. Минимальный AVI с видеопотоком (`strf` 40 байт) и звуковым потоком IMA ADPCM (`strf` 20 байт) даёт ровно 336:
  12 + 12 + 64 + (12+64+48) + (12+64+28) + 12 + 8.
- В нашем тесте обычный AVI от ffmpeg по умолчанию содержит кадры с `JFIF` и начинает первый кадр с байта 9994 (JUNK по 4 КиБ,
  `vprp`, `LIST INFO`), поэтому отвергается. [`tools/make_player_avi.py`](../tools/make_player_avi.py) отдаёт кодирование
  MJPEG и IMA ADPCM ffmpeg'у, а потом пересобирает потоки в нужную раскладку (JFIF заменяется на AVI1, индекс `idx1`).
- AMV: родной мультиплексор ffmpeg (`-c:v amv -c:a adpcm_ima_amv -ac 1 -ar 22050 -block_size 1470`, высота кадра кратна 16,
  размер блока = частота звука / fps) даёт заголовок, который разбор из прошивки принимает.
- Картинка вписывается в экран с сохранением пропорций, увеличение не больше 1,7 раза (по функции подгонки `0x1205FC`);
  по документации SDK экран 128x160 (**unverified** для этого экземпляра).

**На настоящем плеере не проверено:** пределы аппаратного JPEG-декодера, примет ли звуковой плагин IMA ADPCM «как в WAV»
или ждёт вариант AMV, и как плеер относится к нулевым размерам RIFF и LIST, которые ffmpeg пишет в AMV. Про результат
конвертера известно лишь то, что он проходит **разбор заголовка из самой прошивки** (в эмуляторе) и является корректным AVI для
ffmpeg. Сообщения от владельцев настоящих плееров очень приветствуются.
